# Code review: M8a (Blazor portal BFF + admin screens)

Reviewer: Code Review Agent. Date: 2026-10-08.
Scope: `src/Web/Blazor` (Security/, Services/Api/, Pages/Admin/, Components/Admin|Forms, Program.cs), `tests/Web.ComponentTests`, `tests/Api.IntegrationTests/PortalBffEndToEndTests.cs`.

## Verdict: CHANGES-REQUESTED

No Blocker. Seven Major findings (resource leak in the session lock table, stale authorization snapshot, no cancellation / stale-response handling, a 30 s timeout that breaks a documented long-running action, swallowed errors in the issue-license flow, large untested admin surface, unbounded duplication of the dialog/confirm/reload choreography). The architecture is sound: the dependency rule holds (Architecture.Tests pass), pages talk only to typed `I*ApiClient`s returning `ApiResult<T>`, tokens never leave the server, the BFF wiring is clear and fail-closed (stub clients refused outside Development/UiDemo, https-only API URL, `AllowedHosts` and `ForwardedHeaders` guards).

| M1 | `Security/SessionStore.cs:46,79,93,135,140`; `Security/TokenRefresh.cs:67,73,80,104` | Per-session `SemaphoreSlim` tables (`_locks`) are created on login (`SaveAsync` -> `LockFor`) but only removed by `RemoveAsync`/`GetAsync` of an expired entry. A user who closes the browser never triggers a read, the distributed-cache entry expires silently, and the semaphore stays forever: unbounded growth, one entry per abandoned login (twice: store and coordinator). Secondary: `RemoveAsync` is called from `UpdateAsync` -> `GetAsync` while that same lock is held and then removes it, so the next caller creates a second semaphore and two writers can run at once; `TokenRefreshCoordinator` does the same (`TryRemove` while waiters hold the old instance), which can allow two refreshes with one rotating refresh token, exactly what the class comment says must never happen (the API treats replay as theft). | Never remove locks on the happy path. Either use a fixed striped lock array (for example 64 `SemaphoreSlim` selected by hash of the id: bounded, no lifecycle), or evict by age with a timestamp and sweep. Apply to both classes (extract one small `KeyedLock` helper: also removes the duplicated pattern). Add a test: 1000 sessions saved and abandoned must not grow the lock table; concurrent `UpdateAsync` + `RemoveAsync` keeps exclusion. |
| M2 | `Security/PortalAuth.cs:48-66`, `Security/TokenRefresh.cs:113-119`, `Pages/Admin/Roles.razor:97` | Roles, permissions and `MustChangePassword`-adjacent profile data are snapshotted at sign-in; refresh updates only the tokens. ## Refactor suggestions (ordered by value)

1. `KeyedLock` helper with bounded memory (M1, D9).
2. `LoadState<T>` + cancellation plumbing through `LoadData` and the API clients (M3, D2, m8, m14).
3. `SaveAsync`/`ConfirmAndApplyAsync` dialog helpers (D1, D3, D4, M5, m5, M7).
4. Per-call timeout on `ApiCallOptions` (M4) and a profile refresh on token rotation (M2).
5. Typed constants for statuses, scopes and setting types (m12) and `UiText` date helpers (D7).
6. Split `LicenseDetail`, `CreateClient` and extract the settings mapper (m16) once the tests from M6 exist.

## What is good (keep)

- Strict BFF boundary: opaque HttpOnly cookie, encrypted server-side session payload, session fixation avoided (new id each login), refresh-token single flight, replayed-refresh handling, cookie validation against the store, 30 s authentication revalidation per circuit.
- Safe-by-default configuration guards with tests (`StartupGuardTests`), `ReturnUrl` open-redirect protection, header sanitising of the login `ref`.
- `ApiGateway` never throws to pages; `ProblemMapper` hides raw server text for 5xx; correlation ids are surfaced to the user.
- Component library reuse is good: `PageState`, `DataTable` (with request-id stale-response guard), `FormDialog`, `ConfirmDialog`, `StatusChip`, `PermissionMatrix`, consistent `data-testid` use and `aria-label`s on icon buttons; dashboards unsubscribe from `DashboardRangeState` in `Dispose`.
- All admin pages inherit `PlatformPortal` from `Pages/Admin/_Imports.razor` plus a per-page permission policy (AND semantics), and the CSV endpoint requires both.
- Component tests are deterministic (`WaitForAssertion`, fake clock, scripted API, no `Sleep`/`Delay`), and cover the auth/policy matrix well.
