# Security review: M7 Usage & Dashboards

Reviewer: Security Agent. Baseline: docs/04 (T1-T12), docs/03, docs/02. Scope: merge 727f801 (M7 on top of M6). Static review only; Docker tests were not run and no product code was changed.

Tools: `dotnet list package --vulnerable --include-transitive` ran and found nothing in any project. gitleaks is not installed, so secret scanning was not run. I grepped for `IgnoreQueryFilters`, `FromSql` and `MarkupString` in the changed code and found none.

## Verdict: PASS-WITH-CONDITIONS

There are no Critical or High findings. Tenant isolation, authorization, CSV neutralisation and audit ordering hold. The conditions are Medium items M1 and M2, which should be fixed or accepted before production. The other findings are Low or Info.

## Checked and found sound

1. **Tenant isolation.** No `IgnoreQueryFilters`, no raw SQL and no client input anywhere in the changed code. Every client query comes from `ICurrentUser.ClientId` and the `AppDbContext` filter plus RLS. `ClientDashboardService.cs:57` and `UsageReportService.ExportClientAsync:155` and `NotificationService.cs:244,260` return 403 when `ClientId` is null, so a platform user, whose filter would otherwise show every tenant, can never reach the client path. The recognition, top-keys and notification queries have no explicit `ClientId` predicate; they depend on the filter and RLS, which fail closed. Explicit predicates would be cheap defense in depth.
2. **Strict tables.** The admin path reads only `LicenseTransactions`, `ApiRequestLogs`, `Licenses`, `Clients`, `ApiKeys`, `WebhookDeliveries` and `WebhookEndpoints`, all non-strict aggregates. It never reads `RecognitionRequests` (`IStrictTenantOwned`), so no per-person data is exposed. Admin output contains only counts, credit totals, client code and name, and license names.
3. **Authorization.** All 7 endpoints have `[HasPermission]`. Platform and client scope are separated in `PermissionAuthorizationHandler`. API-key principals hold only issued scopes and `ApiKeyScopes.Assignable` is faces-only, so a key cannot reach dashboards, reports, notifications or verify-ledger. `licenses.verify-ledger`, `dashboard.admin` and `reports.read` are Platform scope and are seeded to SuperAdmin via `IdentitySeeder` sync, with no client role gaining them.
4. **RLS.** `LicenseAlert` is `ITenantOwned`, so `RowLevelSecurityScriptBuilder.TenantTables` (model-derived) and `TenantModelRules` cover the new table. `DatabaseInitializer` re-installs RLS at start-up, so the migration needs no separate policy. Filter, block predicates and FK to `Clients` are in place.
5. **Alert job.** Candidates are read in platform scope read-only. Each alert is raised in `BeginTenant(clientId)` with the alert row and webhook rows committed together. The unique `(SubjectId, AlertType, Bucket)` index with `UniqueConstraintViolationException` handling is multi-node safe. Payloads carry no personal data or secrets (API key alerts expose only the non-secret prefix).
6. **CSV.** The export audit entry is written and saved before streaming starts. The range is capped at 92 days both in the validator and the service. The aggregation is `GROUP BY` in SQL, so the output is bounded rows and streamed. The filename is built from dates only (no header injection). `Cache-Control: no-store`. Quote, comma and newline escaping is correct. Cell types are whitelisted.
