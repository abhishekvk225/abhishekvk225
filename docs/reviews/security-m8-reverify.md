# Security re-verification: M8a and M8b fixes

Reviewer: Security Agent (independent). Date: 2026-10-08. Method: static review of the merged code plus a read of the new tests. Tests were not executed (no Docker/DB). No product code changed.
Baseline: `docs/reviews/security-m8a.md`, `docs/reviews/security-m8b.md`. Fix commits: `893b3a3` (M8a), `eaf0f0e`..`8e3fb19` (M8b).
Tools: `dotnet list package --vulnerable --include-transitive` on `NexaVerify.Web`: no vulnerable packages (ran). gitleaks: binary not installed (CI runs it, `.github/workflows/ci.yml`). Grep for `MarkupString` and `IgnoreQueryFilters` in the portal: no hits.

## Verdict: PASS-WITH-CONDITIONS

No Critical, High or Medium finding remains. Both Mediums (M-1, M-2 of M8a; M8b-01, M8b-02) are fixed and covered by tests that would fail without the fix. The remaining items are Low/Info hardening (listed under "Open items"); none blocks release. Conditions are tracking items only: the two worth scheduling are the `Testing` environment relaxation (R-1) and the missing per-user upload concurrency cap (M8b-03).

## Focus questions

- **Forwarded end-user IP (forgot/reset/refresh): can a user spoof it?** No, in the default configuration. The value comes from `HttpContext.Connection.RemoteIpAddress` (`App.razor:49`, `AuthEndpoints.cs:171`), never from a request header the portal copies, and the portal never forwards incoming `X-Forwarded-For`. It reaches the circuit as a protected root-component parameter, and is persisted in the encrypted session for refresh. The only spoof path is a mis-set trust list (`ForwardedHeaders:*` on the portal accepting the attacker's hop), which the `/0` guard narrows; the API must also list the portal in its own `KnownProxies`, otherwise the header is ignored and the shared-bucket problem returns (documented in `deploy/CONFIG.md:93`). Deployment note: if the portal sits behind a proxy and `ForwardedHeaders` is not enabled, every visitor shares the proxy's address.
- **ForwardedHeaders `/0`:** rejected for IPv4 and IPv6 (see N-3 for the split-range residual).
- **Sign-out CSRF:** closed for cross-site and same-site initiators and for non-browser clients without the header. Residual N-1.
- **`__Host-` prefix compatibility:** session cookie meets all prefix rules. N-2 for antiforgery under a path base.
- **Production guards by environment name:** only `Development` relaxes the security-setting guards. `Testing` still relaxes the API-scheme and key-persistence guards (R-1).
- **Striped lock correctness:** it is a ref-counted keyed lock, not a striped array; correct as analysed in L-5.
- **Passive polling not sliding the session:** confirmed on every path (above).
- **Camera frame cap:** enforced server-side before any buffering (above).
- **Idempotency key reuse:** no wrong replay and no cross-request/cross-tenant leak (derived key includes client, operation, image hash and request fingerprint).
- **CSV relay same-origin check:** accepts only `Sec-Fetch-Site: same-origin` or `none`; an absent header is refused with 403 (tested in `SignOutRequestOriginTests` for the shared helper). The check runs after authentication/authorization and before the throttle, so cross-site requests cannot burn a victim's export quota. Residual N-1.
- **DownloadThrottle bypass:** keyed on the server-side session id (not client controlled), 6 per minute, memory pruned above 2,000 entries. Bypass requires a second valid session (a second sign-in, itself limited by the API's per-IP auth limit). Per-process only. Info (N-4).
